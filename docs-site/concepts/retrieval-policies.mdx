# Políticas de Retrieval

Una política de retrieval es un documento versionado, separado del mapping, que controla comportamiento de consulta en caliente. Puede ajustar por entidad:

- sinónimos léxicos;
- aliases de campos;
- comportamiento implícito `filter`, `prefer` o `search`;
- boost de preferencias;
- pesos lexical/vector de la fusión RRF.

<Info>
  Crear, evaluar o activar una política no modifica `records`, embeddings ni
  `sources.maturityStatus`. Una fuente `agent_ready` permanece disponible durante todo el flujo.
</Info>

## Mapping vs. política

Usa una política para cambios que solo afectan el query-time:

- términos equivalentes del negocio;
- nombres comerciales, regionalismos y errores frecuentes;
- vocabulario estacional que ya existe en los campos indexados.
- aliases con los que un usuario menciona un campo;
- decisión temporal de filtrar, priorizar o conservar una coincidencia en texto libre;
- calibración de boosts y pesos RRF.

Modifica el mapping y reindexa cuando cambien campos `searchable`, `searchWeight`, `cardinality`, operadores predeterminados, reglas, filtros, entidades o `embeddingTextTemplate`. Una política no puede hacer searchable ni filterable un dato que el mapping no permite.

Al consultar, el Gateway carga en batch la política activa. Los aliases de policy se agregan a los aliases del mapping. Si la policy contiene sinónimos para la entidad, reemplazan los sinónimos legacy de esa entidad; si no la cubre, el mapping sigue como fallback.

## Documento de ejemplo

```json
{
  "document": {
    "entities": [
      {
        "entity": "variant",
        "synonyms": {
          "entries": {
            "vinipiel": ["piel sintética", "ecocuero"],
            "retapizar": ["tapicería", "tapizar"]
          }
        },
        "fields": [
          {
            "field": "collections",
            "aliases": ["línea", "temporada"],
            "implicitBehavior": "prefer",
            "boost": 0.35
          }
        ],
        "rrf": {
          "lexicalWeight": 1,
          "vectorWeight": 1.1
        }
      }
    ]
  },
  "expectedActiveVersion": 3
}
```

Una entidad debe definir al menos `synonyms`, `fields` o `rrf`.

### Configuración por campo

- `field`: nombre público exacto del mapping.
- `aliases`: nombres adicionales que el usuario puede emplear.
- `implicitBehavior`: solo controla coincidencias implícitas en texto libre. Una mención explícita como `"color blanco"` sigue siendo filtro duro.
- `boost`: fuerza de la preferencia entre `0` y `1`.

El campo debe existir, ser visible, no sensible y filterable en el mapping activo. La cardinalidad y el operador predeterminado siguen perteneciendo al mapping.

<Warning>
  Aunque el contrato de policy reserva `valueAliases` y `match`, no los uses como overrides
  operativos hasta que aparezcan reflejados en capabilities. Envía valores canónicos de
  `suggestedValues` y define `match` en el mapping.
</Warning>

### Pesos RRF

- `lexicalWeight`: peso positivo de la búsqueda full-text.
- `vectorWeight`: peso positivo de la similitud semántica.

Empieza con los valores del mapping y cambia los pesos solo con evals representativos. Un peso mayor no garantiza mejor calidad para todos los queries.

## Estados y activación

Cada versión es inmutable:

```text
draft → active → archived
          ↑          |
          └─ rollback┘
```

1. `POST /sources/{id}/retrieval-policies` crea un `draft`.
2. `POST /sources/{id}/retrieval-policies/{version}/eval` ejecuta el eval set específico del source sin cambiar tráfico.
3. `POST /sources/{id}/retrieval-policies/{version}/activate` exige `score >= threshold` y `sensitiveLeaks = 0`.
4. Activar una versión archivada ya validada restaura esa versión en O(1).

`expectedActiveVersion` implementa control de concurrencia optimista. Usa `0` al crear o activar la primera versión y la versión activa conocida en operaciones posteriores.

## Seguridad y auditoría

- Scopes mínimos: `retrieval:read` y `retrieval:write`.
- RLS y validación de ownership por `workspace_id`.
- Entidades limitadas a las que existen en el mapping activo.
- Campos limitados a campos filterable, visibles y no sensibles del mapping activo.
- Términos vacíos, auto-sinónimos y duplicados normalizados se rechazan.
- Cada eval run conserva el `retrievalPolicyId` evaluado.

Configura primero el contrato estable en [Búsquedas y Filtros](/onboarding/configure-search). Para un cambio solo de vocabulario, sigue [Actualizar sinónimos](/onboarding/synonym-updates).

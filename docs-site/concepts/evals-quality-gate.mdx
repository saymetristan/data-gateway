# Evals como Compuerta de Calidad

Los LLMs pueden ser impredecibles. Para asegurar que tus usuarios o tus flujos automatizados tengan experiencias confiables, el Data Gateway implementa un sistema de **Evaluaciones (Evals)** obligatorio.

No puedes marcar una fuente como `agent_ready` si no tienes Evaluaciones aprobadas.

## ¿Por qué evaluar?

Cuando el agente de IA llama a la herramienta `search_product(query="camiseta roja")`, el gateway ejecuta su algoritmo de búsqueda híbrida. Las *Evals* son "pruebas unitarias" sobre este algoritmo aplicado a **tus datos**. Verifican que la búsqueda "camiseta roja" de verdad devuelve en primer lugar el `ID` de la camiseta roja en tu base de datos, y que los filtros semánticos (si los definiste) están funcionando correctamente.

## Sets y Casos de Evaluación

Un **Evaluation Set** contiene múltiples preguntas típicas de tu negocio (**Cases**).

Para cada caso (query), defines aserciones. Al menos una es obligatoria:

| Aserción | Efecto |
| --- | --- |
| `expectedExternalIds` | Los IDs de origen deben aparecer en el top-k (precision@k) |
| `expectedTopIds` | Orden exacto del prefijo de resultados |
| `mustRankAbove` | `{ "higher": "id-a", "lower": "id-b" }` — a debe salir antes que b |
| `mustApplyFilters` | El run debió aplicar esos filtros duros |
| `mustApplyPreferences` | El run debió aplicar esas preferencias blandas |
| `mustNotContainFields` | Ningún resultado puede filtrar campos sensibles |
| `mustNotAppearInTop` | `{ "ids": ["id-a"], "k": 3 }` — esos IDs no pueden aparecer en el top K |
| `maxResultCount` | Límite de resultados permitido; usa `0` cuando la respuesta correcta es vacía |
| `maxConfidence` | Techo de confidence del envelope para consultas sin evidencia suficiente |
| `mustContainFields` | Todos los resultados deben incluir los campos visibles indicados, por ejemplo `item_code` |

Si un case quedó mal definido, bórralo con `DELETE /evals/sets/:id/cases/:caseId` y vuelve a crearlo antes del run.

Para ranking (filtro vs preferencia), ver [Ranking y Preferencias](/concepts/ranking-and-preferences).

### Ejemplo de flujo
1. Envías una batería de consultas típicas de tus clientes.
2. El Gateway corre el motor híbrido + rescore.
3. Se comparan IDs, filtros, preferencias y ranking.
4. Obtienes un porcentaje de efectividad. Si supera tu **umbral (threshold)** (ej. `0.8`), el set aprueba.

## Activación segura

Si el último resultado de evaluación ("run") supera el umbral y valida exitosamente los campos confidenciales (garantizando cero filtraciones de datos `sensitive`), la fuente pasa a estado `validated`.

Solo en estado `validated` se te permitirá llamar al endpoint `POST /sources/:id/activate`, abriendo el acceso para los agentes MCP.

## Evals de políticas de retrieval

Una policy draft usa el mismo eval set específico del source, pero el run queda ligado a `retrievalPolicyId`. Las consultas se ejecutan contra el draft sin afectar tráfico. Aprobar este run habilita `POST /sources/:id/retrieval-policies/:version/activate`; no promociona ni degrada la madurez del source.
